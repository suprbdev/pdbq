# Upgrading

## 0.x → 1.0

### Catalog format 10 (pdbcore)

- **Regenerate schema caches.** The catalog format is now 10, and `serve`
  refuses caches written by earlier releases (format 9). The error names the
  program that wrote the cache when the cache records it. Run
  `pdbq schema dump` again. New caches record the writer (`pdbq`, its
  version and the pdbcore version).
- **Identity `BY DEFAULT` columns are writable.** A
  `GENERATED BY DEFAULT AS IDENTITY` column is now in `<Type>CreateInput`
  (optional, like a serial column: an omitted value takes the sequence's
  next one) and in `<Type>UpdateInput`. A key on such a column now gets an
  `upsert<Type>By<Key>` mutation. Before, these columns were left out like
  `GENERATED ALWAYS` ones. Identity `ALWAYS` and generated columns are
  unchanged.
- **PostgreSQL minor upgrades are not drift.** The cache hash covers the
  server's major version only, so `pdbq schema check` and the watch poll no
  longer report a PostgreSQL minor upgrade. A major upgrade still counts.
- **Stable overload order.** Functions are ordered by schema, name and
  input parameter types (fewer parameters first). When overloads collide on
  a GraphQL field name, the one kept is now always the overload with the
  fewest parameters. Before, it could change from one run to the next.
- **PostgreSQL 14 is the minimum.** Older servers are refused at
  introspection and on every pool connection, so this also applies when
  booting from a schema cache.

### Identity, strict config and plugin settings

Breaking changes:

- **The `rls` section is gone.** It is split into `auth` (how a request
  proves who it is), `roles` (which database role it runs as) and `claims`
  (how claims reach SQL); see the table below and [RLS](rls.md). An old
  `rls.*` key in the file or a `PDBQ_RLS_*` variable is an error naming its
  new key.
- **`roles.switch: false` is not "auth off".** `rls.enabled: false` used to
  skip authentication too. `roles.switch: false` only stops the role switch:
  credentials are still verified (an invalid token is still a 401) and
  claims are still set. For no authentication at all, also set
  `auth.mode: none`.
- **Anonymous access is opt-in.** `roles.anonymous` defaults to empty (was
  `anonymous`): a request without credentials is answered `401` with
  `WWW-Authenticate: Bearer`. Set `roles.anonymous: anonymous` to keep the
  0.x behaviour. In `auth.mode: none` with role switching on it is required.
- **Fail-closed authentication.** `pdbq serve` refuses to start in jwt mode
  without `auth.jwt.secret`, `auth.jwt.secret_file` or `auth.jwt.jwks_url`,
  and in headers mode without `auth.headers.trusted_proxies` (an empty list
  used to trust every peer). Claim headers from an untrusted peer are a
  401. A role claim that is not a non-empty string is an invalid token
  (it used to fall back to the default role), and a credential that
  resolves to no role is refused.
- **Claims are `jwt.claims.*`.** The per-claim settings moved from
  `pdbq.claims.<claim>` to `jwt.claims.<claim>` (PostGraphile's namespace).
  Update policies, or set `claims.prefix: pdbq.claims` to keep them.
- **Strict configuration.** Unknown keys in the YAML file are errors, and so
  are `PDBQ_*` variables inside a config section (`PDBQ_LIMITS_MAX_DPETH`);
  the error suggests the closest key. Other `PDBQ_*` variables are ignored.
  `log.format` must be `text` or `json`.
- **Plugin names are snake_case**, with no aliases: `smart_comments`,
  `simple_names`, `advanced_filters`, `nested_mutations` (`postgis`,
  `contrib` and `aggregates` are unchanged). This applies to
  `plugins.disabled`, `plugins.settings.<name>`, `pdbq plugins list` and the
  `nested_mutations: … matched 0 rows` error prefix. An unknown name in
  `plugins.disabled` is an error (with a "did you mean" hint).
- **Plugin settings are typed.** `plugins.settings` only accepts the keys of
  each plugin (see [Configuration](configuration.md)); a misspelt key is an
  error instead of being ignored. Environment values such as
  `PDBQ_PLUGINS_SETTINGS_ADVANCED__FILTERS_RELATIONS=false` now reach the
  plugin (they used to be strings the plugins ignored).
  `plugins.settings.nested_mutations.max_depth`/`max_operations` must be
  `>= 1` and `aggregates.scan_cost` `>= 0`.
- **`database.statement_timeout` defaults to `25s`** (was `30s`), below the
  30s `server.request_timeout`, so a slow statement fails with SQLSTATE
  `57014` before the request is cut off.
- **CLI identity.** `pdbq query`, `pdbq schema dump|check|print` and
  `pdbq plugins list` always run with `auth.mode: none` and
  `roles.switch: false`, as the connection role without claims (see
  [CLI](cli.md)). They work on a default config without a JWT secret.
- **Flags.** `--rls.enabled` is replaced by `--roles.switch`; `--auth.mode`,
  `--roles.anonymous` and `--database.statement_timeout` are new.
- **`pdbq config init`** writes `auth: {mode: none}` and
  `roles: {switch: false}` instead of `rls: {enabled: false}`.
- **Embedding.** `pdbq.RLSConfig` is gone (`pdbq.AuthConfig`,
  `pdbq.RolesConfig`, `pdbq.ClaimsConfig`, `pdbq.JWTConfig`,
  `pdbq.HeadersConfig` replace it); `Config.Plugins.Settings` is the typed
  `pdbq.PluginSettings` instead of a map; `config.LoadUnvalidated` and
  `Config.ConnectionIdentity` back the CLI loader.

Also new: `auth.jwt.secret_file`, `auth.jwt.leeway`,
`auth.jwt.role_claim_path` (paths such as `app_metadata.role`),
`auth.headers.role_claim`, `claims.json_setting` (e.g.
`request.jwt.claims`, for PostgREST/Supabase policies), case-insensitive
`Bearer`, `WWW-Authenticate` challenges on 401s (exposed to CORS clients
through `Access-Control-Expose-Headers`), and SQLSTATE class 21
(`more than one row returned by a subquery used as an expression`) reported
as a user error with its message in `errors.detail: prod`.

### Configuration regrouped

pdbq 1.0 nests the flat `server.*` keys into sections, and uses the same
names as pdbr for the concepts both products share (`limits.*`,
`transactions.partial.*`, `schema.domains`, `aggregates.enabled`). Every
item below is breaking. Loading an old key fails and names its new place
(`unknown key server.max_cost: moved to limits.max_cost`, and for
variables `PDBQ_SERVER_MAX__COST ... moved to PDBQ_LIMITS_MAX__COST`).

- **New sections.** `limits` (request limits), `persisted_queries`,
  `subscriptions`, `live`, `incremental` and `server.document_cache`; see
  the table below and [Configuration](configuration.md). Flags follow the
  keys (`--limits.max_cost`, `--subscriptions.enabled`, …).
- **`server.introspection: true` replaces `server.disable_introspection`
  and `server.expose_schema`.** The polarity is inverted
  (`disable_introspection: true` is `introspection: false`), and the SDL at
  `/schema.graphql` is now served whenever introspection is on, which is
  the default: it exposes nothing introspection does not. Both products now
  publish their schema document by default (pdbr: `openapi.enabled`); set
  `server.introspection: false` in production to hide the schema shape.
- **Aggregates have a top-level section.** `plugins.settings.aggregates.*`
  moved to `aggregates.*` (`aggregates.enabled` is the gate, named as in
  pdbr). The plugin is still called `aggregates` in `plugins.disabled`.
- **Partial mutations.** `transactions.partial_mutations` is
  `transactions.partial.enabled`, and the new
  `transactions.partial.max_items` (default 1000, as in pdbr) rejects a
  partial request with more mutation root fields.
- **Mutations always run in a transaction.** `transactions.mutations` and
  `plugins.settings.nested_mutations.force_transactions` are removed (they
  fail as unknown keys). A single statement is atomic anyway, the custom
  mutation payload pair, nested mutations and partial mutations already
  forced a transaction, and every request with a role or claims needs one;
  turning it off only made a multi-field mutation operation non-atomic.
  `op.ForceTx` stays for plugins that need a transaction around a query.
- **No magic zero values.** `incremental.max_responses` defaults to `5`
  and must be `>= 1` and below `database.max_conns` (`0` used to mean half
  of the pool). `subscriptions.subscribe_rate` must be `>= 1` (`0` used to
  disable the limit; set a large value instead). Every `limits.*` key must
  be `>= 1`.
- **Errors name the new keys**, for example `partial mutations are
  disabled: set transactions.partial.enabled` and `live.enabled requires
  subscriptions.enabled`.
- **Embedding.** `pdbq.Config` gains `Limits`, `PersistedQueries`,
  `Subscriptions`, `Live`, `Incremental` and `Aggregates` (types
  `pdbq.LimitsConfig`, `PersistedQueriesConfig`, `SubscriptionsConfig`,
  `LiveConfig`, `IncrementalConfig`, `AggregatesConfig`, plus
  `DocumentCacheConfig` and `PartialConfig`); `ServerConfig` keeps only the
  HTTP keys plus `DocumentCache`;
  `Schema.DomainScalars` is `Schema.Domains`; `TX` has `Partial` instead of
  `PartialMutations` and no `Mutations`; `Config.IncrementalResponses` is
  gone; `nestedmutations.Settings` has no `ForceTransactions` and the
  plugin is no longer a request hook.

### Cost estimate prices unbounded connections at a full page

A connection or list field given neither `first` nor `last` was costed as
10 rows, but it fetches up to `limits.max_page_size` rows (100 by default),
so the per-row work below it (headlines, raster statistics, scores, nested
lists) was under-priced about tenfold. It is now costed as a full page,
like pdbr's limitless embeds, and the default `limits.max_cost` is
`100000` (was `10000`, the same default as pdbr) so common two-level
queries still pass: `allUsers { nodes { … postsByAuthorId { nodes { … } } } }`
with three or four fields per level costs 40,000 to 50,000. A third unbounded
level is rejected; give it a `first`. Queries with explicit `first`/`last`
cost what they did, so the larger default admits about ten times more
explicit work; set `limits.max_cost: 10000` to keep the old budget. A
connection's `totalCount`, `pageInfo`, `aggregates` and `groupedAggregates`
are no longer multiplied by its page size: they are computed once per
connection, so only `nodes` and `edges` repeat per row.

### Default naming

pdbq's default names are now PostGraphile v4's, and `simple_names` is an
opt-in. Relation names depend on the schema alone, never on which other
fields exist.

| Before | After | Notes |
|---|---|---|
| `simple_names` on by default (`users`, `user(id:)`, `updateUser`) | off by default (`allUsers`, `userById`, `updateUserById`) | `plugins.settings.simple_names.enabled: true` restores the short names; `plugins.disabled: [simple_names]` is no longer needed for verbose names |
| forward relation `author` (both modes) | `userByAuthorId` by default; `author` with `simple_names` | also on mutation payloads, in filters (`userByAuthorId: UserFilter`, `userByAuthorIdExists`), orderBy (`USER_BY_AUTHOR_ID__EMAIL_ASC`) and nested-mutation inputs (`userByAuthorId: PostUserByAuthorIdNestedInput`) |
| forward name from the first FK column without `_id`/`Id`, for every key (`created_by` → `createdBy`, `(org_id, user_id)` → `org`) | with `simple_names`, the column without the suffix only for a single-column key ending in `_id`/`Id`; any other key keeps the verbose name | `userByCreatedBy`, `orgMemberByOrgIdAndUserId` |
| `simple_names` backward name `posts` when the child table has at most one FK in total | `posts` when the child table has exactly one FK to this parent; otherwise `postsByAuthorId` | counted per child → parent pair: `transfers` with `from_id`, `to_id` → `users` and `memo_id` → `memos` gives `User.transfersByFromId`, `User.transfersByToId` and `Memo.transfers` |
| a forward relation named like a column or an earlier relation fell back to `<referencedTable>By<Columns>` | schema build error naming the type, the field, the constraint and the fix | rename with `@fieldName` (forward) or `@foreignFieldName` (backward) on the constraint, or switch naming mode; also a conflict with a computed column |
| a payload relation named like a payload field (`query`, …) fell back to `<referencedTable>By<Columns>` | left out of that payload with a build warning | the row field still reaches it (`createRun { run { query { … } } }`) |
| `@name` on a referenced table did not reach forward relation names | it does (`customerByAuthorId`) | as for every other derived name |
