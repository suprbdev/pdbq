# Upgrading

## 0.x → 1.0

### Catalog format 10 (pdbcore)

- **Regenerate schema caches.** The catalog format is now 10, and `serve`
  refuses caches written by earlier releases (format 9). The error names the
  program that wrote the cache when the cache records it. Run
  `pdbq schema dump` again. New caches record the writer (`pdbq`, its
  version and the pdbcore version).
- **Identity `BY DEFAULT` columns are writable.** A
  `GENERATED BY DEFAULT AS IDENTITY` column is now in `<Type>CreateInput`
  (optional, like a serial column: an omitted value takes the sequence's
  next one) and in `<Type>UpdateInput`. A key on such a column now gets an
  `upsert<Type>By<Key>` mutation. Before, these columns were left out like
  `GENERATED ALWAYS` ones. Identity `ALWAYS` and generated columns are
  unchanged.
- **PostgreSQL minor upgrades are not drift.** The cache hash covers the
  server's major version only, so `pdbq schema check` and the watch poll no
  longer report a PostgreSQL minor upgrade. A major upgrade still counts.
- **Stable overload order.** Functions are ordered by schema, name and
  input parameter types (fewer parameters first). When overloads collide on
  a GraphQL field name, the one kept is now always the overload with the
  fewest parameters. Before, it could change from one run to the next.
- **PostgreSQL 14 is the minimum.** Older servers are refused at
  introspection and on every pool connection, so this also applies when
  booting from a schema cache.

### Identity, strict config and plugin settings

Breaking changes:

- **The `rls` section is gone.** It is split into `auth` (how a request
  proves who it is), `roles` (which database role it runs as) and `claims`
  (how claims reach SQL); see the table below and [RLS](rls.md). An old
  `rls.*` key in the file or a `PDBQ_RLS_*` variable is an error naming its
  new key.
- **`roles.switch: false` is not "auth off".** `rls.enabled: false` used to
  skip authentication too. `roles.switch: false` only stops the role switch:
  credentials are still verified (an invalid token is still a 401) and
  claims are still set. For no authentication at all, also set
  `auth.mode: none`.
- **Anonymous access is opt-in.** `roles.anonymous` defaults to empty (was
  `anonymous`): a request without credentials is answered `401` with
  `WWW-Authenticate: Bearer`. Set `roles.anonymous: anonymous` to keep the
  0.x behaviour. In `auth.mode: none` with role switching on it is required.
- **Fail-closed authentication.** `pdbq serve` refuses to start in jwt mode
  without `auth.jwt.secret`, `auth.jwt.secret_file` or `auth.jwt.jwks_url`,
  and in headers mode without `auth.headers.trusted_proxies` (an empty list
  used to trust every peer). Claim headers from an untrusted peer are a
  401. A role claim that is not a non-empty string is an invalid token
  (it used to fall back to the default role), and a credential that
  resolves to no role is refused.
- **Claims are `jwt.claims.*`.** The per-claim settings moved from
  `pdbq.claims.<claim>` to `jwt.claims.<claim>` (PostGraphile's namespace).
  Update policies, or set `claims.prefix: pdbq.claims` to keep them.
- **Strict configuration.** Unknown keys in the YAML file are errors, and so
  are `PDBQ_*` variables inside a config section (`PDBQ_LIMITS_MAX_DPETH`);
  the error suggests the closest key. Other `PDBQ_*` variables are ignored.
  `log.format` must be `text` or `json`.
- **Plugin names are snake_case**, with no aliases: `smart_comments`,
  `simple_names`, `advanced_filters`, `nested_mutations` (`postgis`,
  `contrib` and `aggregates` are unchanged). This applies to
  `plugins.disabled`, `plugins.settings.<name>`, `pdbq plugins list` and the
  `nested_mutations: … matched 0 rows` error prefix. An unknown name in
  `plugins.disabled` is an error (with a "did you mean" hint).
- **Plugin settings are typed.** `plugins.settings` only accepts the keys of
  each plugin (see [Configuration](configuration.md)); a misspelt key is an
  error instead of being ignored. Environment values such as
  `PDBQ_PLUGINS_SETTINGS_ADVANCED__FILTERS_RELATIONS=false` now reach the
  plugin (they used to be strings the plugins ignored).
  `plugins.settings.nested_mutations.max_depth`/`max_operations` must be
  `>= 1` and `aggregates.scan_cost` `>= 0`.
- **`database.statement_timeout` defaults to `25s`** (was `30s`), below the
  30s `server.request_timeout`, so a slow statement fails with SQLSTATE
  `57014` before the request is cut off.
- **CLI identity.** `pdbq query`, `pdbq schema dump|check|print` and
  `pdbq plugins list` always run with `auth.mode: none` and
  `roles.switch: false`, as the connection role without claims (see
  [CLI](cli.md)). They work on a default config without a JWT secret.
- **Flags.** `--rls.enabled` is replaced by `--roles.switch`; `--auth.mode`,
  `--roles.anonymous` and `--database.statement_timeout` are new.
- **`pdbq config init`** writes `auth: {mode: none}` and
  `roles: {switch: false}` instead of `rls: {enabled: false}`.
- **Embedding.** `pdbq.RLSConfig` is gone (`pdbq.AuthConfig`,
  `pdbq.RolesConfig`, `pdbq.ClaimsConfig`, `pdbq.JWTConfig`,
  `pdbq.HeadersConfig` replace it); `Config.Plugins.Settings` is the typed
  `pdbq.PluginSettings` instead of a map; `config.LoadUnvalidated` and
  `Config.ConnectionIdentity` back the CLI loader.

Also new: `auth.jwt.secret_file`, `auth.jwt.leeway`,
`auth.jwt.role_claim_path` (paths such as `app_metadata.role`),
`auth.headers.role_claim`, `claims.json_setting` (e.g.
`request.jwt.claims`, for PostgREST/Supabase policies), case-insensitive
`Bearer`, `WWW-Authenticate` challenges on 401s (exposed to CORS clients
through `Access-Control-Expose-Headers`), and SQLSTATE class 21
(`more than one row returned by a subquery used as an expression`) reported
as a user error with its message in `errors.detail: prod`.

### Configuration regrouped

pdbq 1.0 nests the flat `server.*` keys into sections, and uses the same
names as pdbr for the concepts both products share (`limits.*`,
`transactions.partial.*`, `schema.domains`, `aggregates.enabled`). Every
item below is breaking. Loading an old key fails and names its new place
(`unknown key server.max_cost: moved to limits.max_cost`, and for
variables `PDBQ_SERVER_MAX__COST ... moved to PDBQ_LIMITS_MAX__COST`).

- **New sections.** `limits` (request limits), `persisted_queries`,
  `subscriptions`, `live`, `incremental` and `server.document_cache`; see
  the table below and [Configuration](configuration.md). Flags follow the
  keys (`--limits.max_cost`, `--subscriptions.enabled`, …).
- **`server.introspection: true` replaces `server.disable_introspection`
  and `server.expose_schema`.** The polarity is inverted
  (`disable_introspection: true` is `introspection: false`), and the SDL at
  `/schema.graphql` is now served whenever introspection is on, which is
  the default: it exposes nothing introspection does not. Both products now
  publish their schema document by default (pdbr: `openapi.enabled`); set
  `server.introspection: false` in production to hide the schema shape.
- **Aggregates have a top-level section.** `plugins.settings.aggregates.*`
  moved to `aggregates.*` (`aggregates.enabled` is the gate, named as in
  pdbr). The plugin is still called `aggregates` in `plugins.disabled`.
- **Partial mutations.** `transactions.partial_mutations` is
  `transactions.partial.enabled`, and the new
  `transactions.partial.max_items` (default 1000, as in pdbr) rejects a
  partial request with more mutation root fields.
- **Mutations always run in a transaction.** `transactions.mutations` and
  `plugins.settings.nested_mutations.force_transactions` are removed (they
  fail as unknown keys). A single statement is atomic anyway, the custom
  mutation payload pair, nested mutations and partial mutations already
  forced a transaction, and every request with a role or claims needs one;
  turning it off only made a multi-field mutation operation non-atomic.
  `op.ForceTx` stays for plugins that need a transaction around a query.
- **No magic zero values.** `incremental.max_responses` defaults to `5`
  and must be `>= 1` and below `database.max_conns` (`0` used to mean half
  of the pool). `subscriptions.subscribe_rate` must be `>= 1` (`0` used to
  disable the limit; set a large value instead). Every `limits.*` key must
  be `>= 1`.
- **Errors name the new keys**, for example `partial mutations are
  disabled: set transactions.partial.enabled` and `live.enabled requires
  subscriptions.enabled`.
- **Embedding.** `pdbq.Config` gains `Limits`, `PersistedQueries`,
  `Subscriptions`, `Live`, `Incremental` and `Aggregates` (types
  `pdbq.LimitsConfig`, `PersistedQueriesConfig`, `SubscriptionsConfig`,
  `LiveConfig`, `IncrementalConfig`, `AggregatesConfig`, plus
  `DocumentCacheConfig` and `PartialConfig`); `ServerConfig` keeps only the
  HTTP keys plus `DocumentCache`;
  `Schema.DomainScalars` is `Schema.Domains`; `TX` has `Partial` instead of
  `PartialMutations` and no `Mutations`; `Config.IncrementalResponses` is
  gone; `nestedmutations.Settings` has no `ForceTransactions` and the
  plugin is no longer a request hook.

### Cost estimate prices unbounded connections at a full page

A connection or list field given neither `first` nor `last` was costed as
10 rows, but it fetches up to `limits.max_page_size` rows (100 by default),
so the per-row work below it (headlines, raster statistics, scores, nested
lists) was under-priced about tenfold. It is now costed as a full page,
like pdbr's limitless embeds, and the default `limits.max_cost` is
`100000` (was `10000`, the same default as pdbr) so common two-level
queries still pass: `allUsers { nodes { … postsByAuthorId { nodes { … } } } }`
with three or four fields per level costs 40,000 to 50,000. A third unbounded
level is rejected; give it a `first`. Queries with explicit `first`/`last`
cost what they did, so the larger default admits about ten times more
explicit work; set `limits.max_cost: 10000` to keep the old budget. A
connection's `totalCount`, `pageInfo`, `aggregates` and `groupedAggregates`
are no longer multiplied by its page size: they are computed once per
connection, so only `nodes` and `edges` repeat per row.

### Set-returning function lists hold at most a page

A list returned by a set-returning function, a `SETOF` root function
(`searchPosts(term:)`) or a `SETOF` computed column (`User.recentPosts`),
had no `LIMIT` but was costed as 10 rows, so a function over a growing
table could return any number of rows, each with its nested selections,
within `limits.max_cost`. Such a list now holds at most
`limits.max_page_size` items (100 by default), the rows after them are cut
off, and the cost estimate charges it that many rows, like a connection
without `first`. A list that needs more rows pages inside the function (for
example `limit`/`offset` parameters), or is exposed through a table or view
connection instead.

| Before | After |
|---|---|
| `searchPosts(term: "")` returns every matching row | at most `limits.max_page_size` rows |
| `{ searchPosts { … postsByAuthorId { nodes { … } } } }` costs 10 × its selection | `max_page_size` × its selection, so a nested connection below it may now exceed `limits.max_cost` |

### Set-returning mutation result lists hold at most a page

The result list of a volatile `SETOF` function exposed as a custom mutation
(`publishPosts { posts { … } }`) had no `LIMIT` and was costed as 10 rows.
It now holds at most `limits.max_page_size` items (100 by default) and the
cost estimate charges it that many rows, like a `SETOF` query function. The
function itself still runs to completion; only the returned list is cut off.
A function that must return more rows pages inside the function.

| Before | After |
|---|---|
| `publishPosts` returns every row the function returned | at most `limits.max_page_size` rows |
| `publishPosts { posts { … commentsByPostId { nodes { … } } } }` costs 10 × its selection | `max_page_size` × its selection |

### Smaller behaviour changes

| Before | After |
|---|---|
| `server.request_timeout: 0` silently disabled the request timeout | rejected at startup: `server.request_timeout must be >= 1s` |
| `/schema.graphql` was served without credentials even when `roles.anonymous` was empty (and `__schema` on `/graphql` answered `401`) | it requires the same credentials as `/graphql`: `401 auth_required` / `invalid_token` without valid ones unless `roles.anonymous` is set |
| an EWKT filter operand or `near:` reference in another SRID than a `geometry(…, n)` column: `pg:XX000` `invalid geometry` (or an empty result) | `invalid_argument`, `spatial value has SRID m, but the column's SRID is n` |
| under a transaction (role switching, claims, `transactions.per_request`), a query field's database error failed every later root field with `pg:25P02` and added a pathless `internal` error (logged at `ERROR`) | the query runs again with a savepoint per root field: only the failing field reports its error, the others keep their values |
| APQ registered a document before authentication and the document limits, up to 1024 documents of any size | registration only after the request authenticated and the document validated; the store is bounded by `persisted_queries.max_bytes` (8 MiB) and `persisted_queries.max_entry_bytes` (64 KiB), least recently used first |

### Default naming

pdbq's default names are now PostGraphile v4's, and `simple_names` is an
opt-in. Relation names depend on the schema alone, never on which other
fields exist.

| Before | After | Notes |
|---|---|---|
| `simple_names` on by default (`users`, `user(id:)`, `updateUser`) | off by default (`allUsers`, `userById`, `updateUserById`) | `plugins.settings.simple_names.enabled: true` restores the short names; `plugins.disabled: [simple_names]` is no longer needed for verbose names |
| forward relation `author` (both modes) | `userByAuthorId` by default; `author` with `simple_names` | also on mutation payloads, in filters (`userByAuthorId: UserFilter`, `userByAuthorIdExists`), orderBy (`USER_BY_AUTHOR_ID__EMAIL_ASC`) and nested-mutation inputs (`userByAuthorId: PostUserByAuthorIdNestedInput`) |
| forward name from the first FK column without `_id`/`Id`, for every key (`created_by` → `createdBy`, `(org_id, user_id)` → `org`) | with `simple_names`, the column without the suffix only for a single-column key ending in `_id`/`Id`; any other key keeps the verbose name | `userByCreatedBy`, `orgMemberByOrgIdAndUserId` |
| `simple_names` backward name `posts` when the child table has at most one FK in total | `posts` when the child table has exactly one FK to this parent; otherwise `postsByAuthorId` | counted per child → parent pair: `transfers` with `from_id`, `to_id` → `users` and `memo_id` → `memos` gives `User.transfersByFromId`, `User.transfersByToId` and `Memo.transfers` |
| a forward relation named like a column or an earlier relation fell back to `<referencedTable>By<Columns>` | schema build error naming the type, the field, the constraint and the fix | rename with `@fieldName` (forward) or `@foreignFieldName` (backward) on the constraint, or switch naming mode; also a conflict with a computed column |
| a payload relation named like a payload field (`query`, …) fell back to `<referencedTable>By<Columns>` | left out of that payload with a build warning | the row field still reaches it (`createRun { run { query { … } } }`) |
| `@name` on a referenced table did not reach forward relation names | it does (`customerByAuthorId`) | as for every other derived name |

### Mutation shapes

Table mutations take PostGraphile v4's shapes: every create, update,
delete and upsert, bulk ones included, takes exactly one argument, `input`,
of its own input type named after the mutation field
(`UpperCamel(<field>) + "Input"`, so it follows `@name`, `simple_names`
and naming plugins). `clientMutationId` is a field of that input only, never
of the row values, and every payload echoes it. The bulk mutations are
renamed so an uncountable table name (`news`, `series`) no longer gives the
single-row and the bulk mutation the same name.

| Mutation | Before | After |
|---|---|---|
| create | `createUser(input: UserCreateInput!)` with `{email, clientMutationId}` | `createUser(input: CreateUserInput!)` with `{clientMutationId, user: UserInput!}` |
| update by key | `updateUserById(id: Int!, patch: UserUpdateInput!)` (`clientMutationId` in the patch) | `updateUserById(input: UpdateUserByIdInput!)` with `{clientMutationId, id: Int!, userPatch: UserPatch!}` |
| update by unique key | `updateUserByEmail(email:, patch:)` | `updateUserByEmail(input: {clientMutationId, email, userPatch})` |
| delete by key | `deleteUserById(id: Int!, clientMutationId: String)` | `deleteUserById(input: DeleteUserByIdInput!)` with `{clientMutationId, id: Int!}` |
| upsert | `upsertUserByEmail(input: UserCreateInput!)` | `upsertUserByEmail(input: UpsertUserByEmailInput!)` with `{clientMutationId, user: UserInput!}` |
| bulk create | `createUsers(input: [UserCreateInput!]!, clientMutationId:)` | `createManyUsers(input: CreateManyUsersInput!)` with `{clientMutationId, users: [UserInput!]!}` |
| bulk update | `updateUsers(filter:, patch:, clientMutationId:)` | `updateManyUsers(input: UpdateManyUsersInput!)` with `{clientMutationId, filter: UserFilter!, userPatch: UserPatch!}` |
| bulk delete | `deleteUsers(filter:, clientMutationId:)` | `deleteManyUsers(input: DeleteManyUsersInput!)` with `{clientMutationId, filter: UserFilter!}` |
| nested update | `updateById: {id, postPatch: PostUpdateInput!}` | `updateById: {id, postPatch: PostPatch!}` (`PostUpdateByIdInput` and the other nested key inputs keep their names) |
| nested create | `create: [PostCreateInput!]` | `create: [PostInput!]` |

| Type | Before | After |
|---|---|---|
| create values | `UserCreateInput` (with `clientMutationId`) | `UserInput` (without) |
| update values | `UserUpdateInput` (with `clientMutationId`) | `UserPatch` (without) |
| function row argument (`fn(u users)`) | `UserInput` | `UserRowInput` |
| bulk payloads | `CreateManyUserPayload`, `UpdateManyUserPayload`, `DeleteManyUserPayload` | `CreateManyUsersPayload`, `UpdateManyUsersPayload`, `DeleteManyUsersPayload` |
| single-row payloads | `CreateUserPayload`, `UpdateUserPayload`, ... | unchanged |

A call site changes like this:

```graphql
# before
mutation {
  createUser(input: {email: "a@x.io", clientMutationId: "1"}) { user { id } }
  updateUserById(id: 1, patch: {fullName: "Ada"}) { user { id } }
  deleteUserById(id: 1) { deletedUserNodeId }
  updateUsers(filter: {mood: {equalTo: SAD}}, patch: {mood: OK}) { affectedCount }
}
# after
mutation {
  createUser(input: {clientMutationId: "1", user: {email: "a@x.io"}}) { user { id } }
  updateUserById(input: {id: 1, userPatch: {fullName: "Ada"}}) { user { id } }
  deleteUserById(input: {id: 1}) { deletedUserNodeId }
  updateManyUsers(input: {filter: {mood: {equalTo: SAD}}, userPatch: {mood: OK}}) { affectedCount }
}
```

Collisions are now build errors. When two table mutations get the same
root field name, or their input or payload types the same type name (two
tables of the same name in different schemas, a naming plugin mapping two
kinds to one name, an enum named `user_patch`), the schema build fails
naming both, e.g.
`schema: mutation name collision: "createNews" is both the create mutation of table public.news and the create mutation of table app.news; rename the table or column with the @name smart comment, or the generated name in an InflectionHook plugin`.
Before, the first one was kept and a warning logged. A key column whose
field name equals the input's own fields (`clientMutationId`, the
`<row>Patch` field) is an `input field collision` error. Function
(custom) mutations colliding with a table mutation keep the documented
behaviour: the function is skipped with a warning.

A table whose every column PostgreSQL computes keeps a create mutation that
inserts the defaults, `createTick(input: {clientMutationId})`, and has no
bulk create or update (the old update could never set a column). The rows
field of a bulk payload pluralizes the type's last word (`msNews`, was
`msNewses`).

For plugin authors: `inflect.KindUpdateInput` is renamed
`inflect.KindPatchInput`; `inflect.KindMutationInput` (the input type,
`Value` carries the field name) and `inflect.KindManyPayloadTypeName`
(bulk payloads, `Value` carries the field name) are new.
`schema.FieldMeta.Values` names the row values field of a table mutation's
input; `compile.MutationInput`, `compile.InputFieldType` and
`compile.InputKey` read a table mutation's input in a `CompileHook`.
`schema.Builder.RemoveInputType` / `RemoveEnumType` remove a type and
every reference to it, removing an input type that required it (a bulk
update's input requiring its filter) and the mutations taking such an
input, so a `SchemaHook` removing a filter type cannot leave an
unrestricted bulk update.
### Error codes

Every error now carries `extensions.code` from one closed vocabulary
([errors.md](errors.md)), with the codes pdbr uses for the concepts the two
share. Clients that matched on messages can match on codes instead;
messages are unchanged except where the table says so.

| Before (0.x) | After (1.0) |
|---|---|
| database error `"extensions": {"code": "23505"}` | `"code": "pg:23505"` (every SQLSTATE gets the `pg:` prefix; the dev members `detail`, `hint`, `table`, `constraint` are unchanged) |
| nested mutation key matching no row: SQLSTATE `22P02`, message `invalid input syntax for type boolean: "nested_mutations: <path> matched 0 rows"` | code `not_found`, message `nested_mutations: <path> matched 0 rows` |
| keyed update/delete matching no row: `no row matched "<alias>"` without a code | same message, code `not_found` |
| `server.request_timeout` elapsed: `503`, `{"errors":[{"message":"request timeout"}]}` without a JSON content type | `504`, `Content-Type: application/json`, `{"errors":[{"message":"request timeout","extensions":{"code":"timeout"}}]}` |
| role claim outside `roles.allowed` or never assumable: `401` | `403`, code `role_not_allowed` (same `WWW-Authenticate: Bearer error="insufficient_scope"`) |
| missing / invalid credentials: `401` without a code | `401`, code `auth_required` / `invalid_token` |
| body above `limits.max_body_bytes`: `400 malformed request body` | `413`, code `body_too_large` |
| APQ miss: code `PERSISTED_QUERY_NOT_FOUND` | code `persisted_query_not_found` (message `PersistedQueryNotFound` kept) |
| hash-only request with persisted queries off: `400 missing query` | `200`, message `PersistedQueryNotSupported`, code `persisted_query_not_supported` |
| `persisted_queries.only` without a hash; registration with `apq` off | same `400`s, codes `persisted_query_required` / `persisted_query_not_supported` |
| unknown path or method: the mux's `text/plain` `404 page not found` / `405 Method Not Allowed` | JSON error, codes `not_found` / `method_not_allowed` (`Allow` kept) |
| other `400`, `405`, `406`, `415`, `500`, `503` bodies without a code | codes `invalid_request`, `method_not_allowed`, `not_acceptable`, `unsupported_media_type`, `internal`, `unavailable` |
| GraphQL parse, validation, limit, policy and compile errors without a code | `graphql_parse_failed`, `graphql_validation_failed`, `document_limit_exceeded`, `depth_exceeded`, `cost_exceeded`, `page_size_exceeded`, `introspection_disabled`, `introspection_limit_exceeded`, `read_only`, `partial_mutations_disabled`, `operation_not_supported`, `invalid_argument`, `invalid_cursor`, ... |
| a dropped database connection: `internal error` | `database unavailable`, code `unavailable` |
| a `RequestHook` error: its message, no code | its message, code `operation_rejected` (a `*gqlerror.Error` that carries a code keeps it) |
| WebSocket subscription caps, topic and stream errors without a code | `subscription_limit_exceeded`, `unavailable`, `invalid_argument` |
### Filter, orderBy and smart-tag names

The filter, orderBy and reference-argument names follow one pattern each.
Clients rename the types they declare in variables and the arguments and
values they send; databases rename deprecated behavior tokens.

| Before | After | Notes |
|---|---|---|
| `StringFilterOps`, `IntFilterOps`, `BigIntFilterOps`, `JSONFilterOps`, `StringListFilterOps`, `<Enum>FilterOps`, `<Domain>FilterOps`, … | `StringFilter`, `IntFilter`, `BigIntFilter`, `JSONFilter`, `StringListFilter`, `<Enum>Filter`, `<Domain>Filter`, … | every scalar operator input, as in `postgraphile-plugin-connection-filter`; only variable declarations (`$f: StringFilterOps`) change |
| `GeometryFilterOps`, `RasterFilterOps` | `GeoJSONFilter`, `RasterFilter` | PostGIS |
| `FullTextFilterOps`, `KeyValueHashFilterOps`, `LtreeFilterOps`, `<X>RangeFilterOps`, `<X>MultirangeFilterOps`, `InternetAddressFilterOps`, `StringTrgmFilterOps`, `String[Trgm][Unaccent][Fuzzy]FilterOps`, `IntListIntarrayFilterOps`, `VectorFilterOps`, `VectorDistanceFilterOps`, `CubeFilterOps`, `LatLonFilterOps`, `IntervalFilterOps`, … | the same names ending in `Filter` (`FullTextFilter`, `StringTrgmFilter`, `VectorDistanceFilter`, …) | contrib, interval and domain inputs |
| a table whose `<Type>Filter` equals an operator input name (`strings` → `StringFilter`) shared one GraphQL type | schema build error naming the table and the type | rename the table with `@name` |
| `HavingBigintFilter`, `HavingBigfloatFilter` | `HavingBigIntFilter`, `HavingBigFloatFilter` | aggregates `having` comparisons |
| `having: {AND: […], OR: […]}` | `having: {and: […], or: […], not: {…}}` | lowercase like table filters; `not` is new |
| `postsByAuthorIdExist: Boolean` (backward relations) | `postsByAuthorIdExists: Boolean` | `<relation>Exists` in both directions (forward was already `userByAuthorIdExists`) |
| `POSTS_BY_AUTHOR_ID_COUNT_DESC`, `POSTS_BY_AUTHOR_ID_SUM_ID_DESC` | `POSTS_BY_AUTHOR_ID__COUNT_DESC`, `POSTS_BY_AUTHOR_ID__SUM_ID_DESC` | aggregates relation ordering uses `__` between relation and value, like `USER_BY_AUTHOR_ID__EMAIL_ASC`; with `simple_names`, `POSTS__COUNT_DESC` |
| `near: {geometry: …}` (`NearInput`, one geometry for every spatial column) | `near: {location: …, area: …}` (`<Type>NearInput`, one field per spatial column) | PostGIS distance ordering and `<field>Distance` |
| `nearVector: {embedding: […]}` (`<Type>NearVectorInput`) | `near: {embedding: […]}` | pgvector, bit and cube references |
| `nearPoint: {spot: {lat, lon}}` (`<Type>NearPointInput`) | `near: {spot: {lat, lon}}` | earthdistance references |
| `similarTo: {title: "…"}` argument (`<Type>SimilarToInput`) | `near: {title: "…"}` | trigram and Levenshtein references; the `similarTo` filter operator is unchanged |
| `hstoreKey: {attrs: "size"}` (`<Type>HstoreKeyInput`) | `near: {attrs: "size"}` | key of `<COLUMN>_VALUE_*` ordering; the `<field>Value(key:)` field argument is unchanged |
| PostGIS distance ordering without `near:` was dropped (primary-key order) | an error: `orderBy LOCATION_DISTANCE_ASC requires near: {location: …}` | the same error for every distance, similarity and hstore value ordering |
| a score field (`locationDistance`, `titleSimilarity`, `embeddingCosineDistance`, …) read through a list without its reference was `null` | an error: `field locationDistance requires near: {location: …}` | still `null` on rows read outside a list taking `near:` (lookups, forward relations, payloads) |
| `@behavior -filter` / `-order` | `@behavior -filterBy` / `-orderBy` (PostGraphile V5) | the old tokens still work with a build-time deprecation warning |
| `@filterable` (alias `@sortable`) on foreign keys and computed columns under `relations_opt_in` / `computed_opt_in` admitted both filters and orderings | `@filterable` admits the filter surface, `@sortable` the orderBy surface | tag both to keep both; on columns either tag still admits both past `filters.indexed_only` |
| unknown `@omit` actions and `@behavior` tokens were ignored silently | ignored with a build-time warning naming the object and the token | `@omit reed` no longer goes unnoticed |

### Config messages and embedding API (pdbcore API hygiene)

- **Removed keys say so.** `transactions.mutations` and
  `plugins.settings.nested_mutations.force_transactions` (and their
  `PDBQ_*` variables) are reported as
  `unknown key transactions.mutations: removed: mutations always run in a transaction`
  instead of a bare "unknown key".
- **Doubled underscores after a section are errors.** `PDBQ_ROLES__ALLOWED`
  (and the like) used to be ignored silently, so the setting kept its
  default; it is now `unknown environment variable PDBQ_ROLES__ALLOWED
  (roles_allowed): did you mean PDBQ_ROLES_ALLOWED?`.
- **New checks:** `database.connect_timeout` must be positive (`0` waited
  forever), `database.max_conns` and `database.statement_timeout` must not
  be negative, `auth.jwt.jwks_cache_ttl` must be positive with
  `auth.jwt.jwks_url` (`0` silently meant one hour), and
  `watch.poll_interval` must be positive with `watch.enabled` (`0` crashed
  the polling fallback).
- **`transactions.isolation` errors name the accepted values:**
  `transactions.isolation: "x" is not 'read_committed', 'repeatable_read' or 'serializable'`
  (was `"x" invalid`).
- **Embedding.** `pdbq.LoadConfig(path, flags)` takes the command-line
  values as `map[string]any` (koanf path to value) instead of a
  `*pflag.FlagSet`; build it from a pflag set with
  `cliflags.Changed(fs, except...)` from
  `github.com/suprbdev/pdbcore/confx/cliflags`.
- The smart-comment checks (unknown `@omit` actions, unknown and deprecated
  `@behavior` tokens) now come from pdbcore and are shared with pdbr; the
  warnings are unchanged.
